# M2-B2-A S0：首显机制分析（M1-R 快路径 vs M2-B1-R 慢路径）

基线：分支 `fix/peek-native-m2b1-r`，验收提交 `9dd18a8`。本文所有时间数据来自
`docs/m2-b1-r/evidence/perf-results-{m1r,lab,native}.json` 的逐轮原始记录（4 轮 × 4 样本 × 3 模式，
16/16 有效），采集口径见 `evidence/perf.mjs`（t0 = 捕获期真实点击目标帖时间戳链接，全部戳同原点）。

---

## 1. 核心结论

**M1-R 的 19–20ms 快路径与 ~980ms 慢路径的区别只有一个：M1-R 的阅读副本是在
"点击 → X 提交详情路由并卸载时间线"这个窗口内、从时间线上仍挂载的被点 cell
同步提取渲染的，还是错过了这个窗口、退化为等待 X 自己渲染详情页焦点 cell。**

这是一场 M1-R 输赢随机的竞态：

- M1-R 的路由检测（点击级联计时器 0/60/150/350ms + title MutationObserver）必须先观察到
  URL 已变为 `/status/<id>` 才会启动 `buildReader()`；
- 而 X 一旦提交详情路由就会重渲染主列——时间线 cell 被卸载，之后任何 DOM 提取都只能等
  详情页自己的焦点 cell（实测 X 原生详情首显 ≈ 980ms）；
- 谁先发生决定快慢。**M1-R 无法控制这场竞态，因为它在点击时"看不到"即将打开哪一帖**——
  它的提取动作由"路由已变化"触发，而路由变化与时间线卸载由 X 的同一次 React 提交驱动。

M2-B1-R 没有慢——它的 T1（原生焦点帖可读）与裸 X 原生详情逐轮一致（±22ms，见 §7）。
**~1 秒就是 X 原生详情渲染本身的成本**；M2-B1-R 丢失的是 M1-R 那 25% 命中的快路径，
因为 Native 模式不再建阅读副本，唯一首显载体就是 X 自己的详情渲染。

M2-B2-A 的出路由此确定：**在点击的捕获阶段（X 尚未做任何事）就用被点 cell 的已渲染 DOM
建一个轻量阅读预览，把"等路由变化再提取"变成"点击瞬间提取"**——把 25% 的竞态快路径
变成确定性的首显，随后原生详情与适配器照常接管。

## 2. 八个问题的逐一回答

### Q1 用户点击前，目标帖子在信息流 DOM 里已存在多少内容

时间线/profile 列表中的被点 cell 是一个完整的 `article[data-testid="tweet"]`，点击瞬间已渲染：

| 内容 | 点击时已在 DOM | 备注 |
|---|---|---|
| status id（时间戳链接 href） | ✅ | `focalCellByStatusId` 的判定依据 |
| 作者名、@handle、头像 URL | ✅ | |
| 已显示正文文本 | ✅ | 长帖为折叠态（show-more 截断），非全文 |
| 图片（`pbs.twimg.com/media`） | ✅ | 已加载缩略/展示尺寸的 URL |
| 引用帖摘要（作者/文本/缩略图） | ✅ | 引用卡内已渲染部分 |
| 计数（回复/转推/喜欢/书签） | ✅ | 列表密度下的计数条 |
| 视频 | 元数据层 ✅ | 列表内是 X 原生 `<video>`/播放器壳；**不可把静态海报算作可播放** |
| 评论区 | ❌ | 不在任何列表 DOM 中 |
| 折叠长帖全文 / Article 全文 | ❌ | 详情页水合后才有 |

即：**预览可用的全部数据 = M1-R 快路径第一帧用过的同一批数据**（`extractFocal(expand:false)`
的输入），这正是 M1-R 快路径帧在 19ms 内能做到"准确"的原因。

### Q2 M1-R 在点击事件的哪个阶段捕获这些内容

**不在点击阶段。** M1-R 的捕获期监听器（`route-observer.js onCaptureClick`，document capture）
只做两件事：B3 锚点预提交捕获、武装级联计时器 `[0, 60, 150, 350]ms`。真正的提取发生在
**点击之后的第一次 `checkRoute()` 观察到 URL 已变**时——可能来自：

1. 0ms 级联计时器（点击宏任务结束后的下一个宏任务，此时 pushState 通常已发生）；
2. title MutationObserver 微任务（X 改写 `document.title`，先于或后于路由提交不定）；
3. 60/150/350ms 兜底计时器或 500ms 路由轮询。

提取动作被"路由已变化"这一事实**被动触发**，触发时刻与 X 的卸载时刻无任何协调——竞态的根源。

### Q3 M1-R 何时创建阅读副本

`buildReader()` → `extractFocal(focalId, alive, { expand: false })`：
- 若此时被点 cell 仍在 DOM（快路径）：提取 + `renderPane` **同步完成于同一个任务**（await 的
  是同步完成的 async 函数，仅一个微任务）→ 实测 t0+19–20ms 已可读；
- 若 cell 已被卸载（慢路径）：`extractFocal` 返回 null → `BUILD_POLL_MS=500ms` 轮询，直到
  详情页自己的焦点 cell 出现（~980ms）→ 提取渲染 → T1 ≈ 980–1000ms。

### Q4 X 原生 SPA 何时开始导航

点击时间戳链接后，X 在**同一个点击宏任务内**完成路由意图提交（pushState/replaceState + 启动
详情路由渲染）。可观察证据：0ms 级联计时器执行的 `checkRoute()` 在快、慢两种轮次里读到的
都已是详情 URL（慢路径轮次 500ms 轮询从未提前命中时间线 cell，说明卸载发生在第一轮提取前）。
精确的 pushState 时刻无法在扩展内观测（Navigation API 事件在 ISOLATED world 不可达，
`route-observer.js` 头注记录的 M1-B3 实测结论），但对工程结论无影响：**导航意图在点击任务内
生效，重渲染在紧随其后的 React 提交中卸载时间线**。

### Q5 原生详情页焦点组件何时出现

逐轮实测 T1（同口径：正确 id + 自有时间戳链接 + 非空正文）：

| 样本 | native（裸 X）逐轮 | lab（M2-B1-R）逐轮 |
|---|---|---|
| video | 985/991/956/974 | 986/992/970/983 |
| photos | 974/985/981/985 | 981/979/978/1002 |
| text | 997/981/1005/992 | 985/972/973/**532** |
| highcomments | 986/985/976/984 | 987/1026/**540**/977 |

裸 X 详情焦点帖稳定在 **~980ms**（偶发 ~530–540ms 的快轮次，X 自身波动，与扩展无关——
native 模式没有适配器也同样 ~980ms）。这 ~980ms 里包含 X 的详情路由组件挂载、
TweetDetail 数据就绪与 React 提交；其中哪些是网络、哪些是水合无法在扩展内拆分（§8）。

### Q6 M2-B1-R 何时安装内部适配器

时间链（`reader-lifecycle.js` → `controller.js` → `adapter-core.js`）：

1. `checkRoute()` 观察到详情 URL（t0+0–60ms）→ `onDetailRoute(focalId)` → INSTALL postMessage；
2. MAIN 适配器 `install()`：`focalCellByStatusId` 查焦点 cell——**此刻详情尚未渲染，返回
   UNSUPPORTED "focal-cell-not-found"** → 控制器按 `LAD_INSTALL_RETRY_MS=250ms` 有界重试
   （≤12 次 / 3s 预算）；
3. 详情焦点 cell 出现（~980ms）后的下一次重试成功：定位虚拟列表实例、所有权检查、包装
   `_getFinalRenderedItems`、标记焦点 article → ACTIVE；
4. 控制器校验焦点标记真实在 DOM → 挂分栏 CSS → **T1 = 原生焦点帖可读 ≈ X 自己的渲染时刻**。

适配器从不在 X 渲染路径上制造等待（重试节奏 250ms 远细于 980ms 的渲染粒度；实测同表面
差 −22～+5ms）。

### Q7 什么时候可以无风险地用原生组件接管阅读

**当且仅当**（M2-B1-R 已实现的全部条件，预览交接沿用）：

- URL 指向的焦点 id 与预览/阅读载体一致（身份防伪）；
- 详情页焦点 article 已真实渲染、可被 `focalCellByStatusId` 定位、其自有时间戳链接证明归属；
- 适配器完成所有权检查、包装、article 标记，控制器核验标记后才挂分栏 CSS；
- 接管动作**只发生一次**（session 状态机保证），且任何失败走 CLOSED 回退（预览清除 →
  X 原生单栏照常可用）。

接管风险点与 M2-B1-R 既有防线一一对应：焦点 cell 被虚拟列表回收/重建 → 包装注入 +
health tick 重绑；article 同 cell 替换 → P1-B 观察器；包装被 X 替换 → wrapper-replaced 退出；
恢复失败 → P1-A Residue Lock 拒绝再包装。预览层不得触碰其中任何一环。

### Q8 哪些延迟来自网络、React 水合、路由检测

扩展内无法观测网络（零 webRequest、零主动请求），以下为可证明的分解：

| 延迟段 | 量级 | 归属 | 证据 |
|---|---|---|---|
| 路由检测 | 0–60ms（M1-R 慢路径）/ 0ms（预览方案） | 扩展侧 | 级联计时器粒度；预览方案在捕获期同步完成，≈0 |
| M1-R 提取+渲染副本 | <1ms（cell 在场时） | 扩展侧 | 19–20ms 总帧含点击任务本身 |
| X 详情首显 | **~980ms（主体）** | X 内部（数据就绪 + React 提交） | native 模式同样 ~980ms，扩展全程旁路 |
| 适配器安装 | ≈0（并入 X 渲染时刻） | 扩展侧 | lab − native 同表面差 −22～+5ms |
| 评论候选首现 | +330～+1000ms（逐轮波动大） | X 内部（评论数据/水合） | 三模式同呈双簇（~1.1–1.5s / ~2.0s），native 四轮全慢簇 |

**结论：T1 的 ~980ms 不是扩展制造、也无法被扩展在"原生组件内部"消除；扩展唯一能消除的
是"从点击到第一份可读内容"中属于自己的 0–60ms 与——更重要的——把首显载体从"等 X 详情"
换成"点击瞬间已存在的 DOM"。**

## 3. 完整时间线（点击 → 预览 → 原生详情 → 适配器建立）

以本轮将实现的预览方案为基准（M2-B1-R 现状 = 无 0/1/6 行）：

```
t0        用户点击时间戳链接
          ├─ [扩展·捕获期] onCaptureClick：锚点预捕获 +（新）同步提取被点 cell
          │  → 预览层立即挂载（t≈0–20ms，与 M1-R 快路径同量级）
          ├─ [X·同一宏任务] 路由意图提交（pushState），详情路由渲染排队
t≈0–60    checkRoute 观察到详情 URL：
          ├─ 预览身份核验（目标 id == URL id），不匹配 → 立即清预览
          └─ onDetailRoute → INSTALL（MAIN 适配器收到后因焦点 cell 未渲染而 UNSUPPORTED，
             250ms 有界重试中）
t≈980     X 详情页焦点 article 渲染（网络/水合完成，X 内部成本，扩展无法压缩）
          ├─ 适配器重试命中：定位实例 → 所有权 → 包装 → 标记 article → ACTIVE
          ├─ 控制器核验标记 → 挂分栏 CSS（原生焦点帖固定左栏）
          └─ （新）预览层同一拍移除 → 原生组件无感接管 → T1b 完成
t≈980+    右栏评论列随 X 详情水合继续出现（T2a/T2b）
```

M1-R 快路径在时间线上等价于把上表 0/1 两行替换为"同步建阅读副本"，且**永不发生接管**
（副本就是终点）。预览方案继承其速度，把终点还给原生组件。

## 4. 快路径触发条件与成功率（逐轮数据）

M1-R T1 逐轮（`perf-results-m1r.json`）：

| 样本 | r0 | r1 | r2 | r3 | 快路径命中 |
|---|---:|---:|---:|---:|---|
| video | 979 | 982 | 980 | 981 | **0/4** |
| photos | 982 | 979 | 982 | 977 | **0/4** |
| text | 1001 | **19** | **19** | 975 | **2/4** |
| highcomments | 983 | **19** | 999 | **20** | **2/4** |

**触发条件**（从代码路径 + 逐轮数据反推）：第一次带详情 URL 的 `checkRoute()` 执行时，
被点 cell 仍挂在 DOM 中。胜负手是 X 提交详情路由后的 React 卸载提交与我们的
0–60ms 级联检测之间的先后——扩展不可控。

**成功率的规律**：

1. 总体 4/16（25%）；文/高评论样本 4/8（50%），媒体样本 0/8。
2. text 与 highcomments 的快轮次**完全重合**（都是 r1/r3）——命中与否由轮次级全局时序状态
   （页面新近加载程度/缓存温度影响 X 提交时序）主导，而非帖子内容本身。
3. 媒体样本 8/8 全慢。两个候选解释，均**未经实机证实**、如实标注为假设：
   - 媒体 cell 更重，X 对含播放器/多图的列表提交与详情提交的调度次序不同，窗口更窄；
   - 媒体帖首帧正文校验失败的可能已被排除（若快路径帧已挂载但正文为空，T1 会推迟到
     hydration 刷新而非精确落在 979–982，与慢路径无法区分——无法证伪，但该解释需要
     "快路径帧恰好全部落在与慢路径相同的 980ms 时刻"这一巧合）。

**对 M2-B2-A 的含义**：快路径真实存在、19–20ms 可复现（4 轮中 4 次命中均为 19/20ms，
方差 ≈0），但它是一个 25% 概率的竞态奖品，且媒体帖从未中奖。预览方案在捕获期同步提取，
把窗口从"0–60ms 竞态"变为"点击任务内确定"，从机制上消除该竞态——这是 S1 的设计依据。

## 5. M2-B1-R 的 T1 为什么是 ~1s（诚实表述）

- **不是适配器慢**：同表面 lab vs native 逐轮差 −22～+5ms（M2-B1-R 报告 §T1）。
- **不是测量伪影**：本轮采集器 t0 = 点击戳、零固定 sleep，上次 ~1580ms 已确认废弃。
- **是 X 详情渲染本身**：native 模式（无任何扩展干预）同样本同为 ~980ms。
- M1-R 字面门槛 FAIL（text/highcomments 的 +475/+480ms）由其双峰中位数造成：剔除 <100ms
  浮层快路径后 M1-R 慢路径中位 988/991 vs lab 972.5/982——**慢路径上两者等价**。

## 6. 对本轮指标口径的落点

- **T1a（首个真实可读内容）**：预览正确、可见、身份一致即可计入。预览方案的目标：
  中位数 ≤100ms，与 M1-R 快路径同速（同场景额外延迟 ≤50ms）。
- **T1b（原生 React 内容完成接管）**：沿用 M2-B1-R 的 T1 口径（`article[data-peek-lad-focal]`
  身份+正文校验）。门槛：相对 M2-B1-R 不退化超过 max(50ms, 基线中位数 10%)。
- **T1c（视觉稳定）**：预览→接管过渡的闪烁/重复/布局跳变检查（帧采样 + 不变量断言）。
- 预览数据与 M1-R 快路径同源（§1 表），因此 T1a 的"准确"有既有工程背书：
  同一提取器、同一折叠态语义（show-more 帧标注为折叠，不算全文）。
