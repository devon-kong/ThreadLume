## 右页隐藏研究

1. 原始CSS视频测试 `c1-hide-video.json`：隐藏article 919→0px，cell1004→85px，composer y984→65px；原video仍连接但暂停。深滚3200px后右video卸载，符合右Document自身虚拟化。回顶原生焦点重新挂载。
2. 实际content.bundle + mock runtime测试 `c1-content-video.json`：1440×900、1280×800、1000×760。发现隐藏已滚走的焦点造成回复框偏出视口；1000组程序scroll被尚未完成的自动定位覆盖，**该组不算深滚通过**。
3. 一轮修复：显式开启隐藏后回到composer；真实wheel触发用户接管；修复组 `c1-content-video-repair.json` 三视口分别深滚6401/6381/6421px，原焦点都卸载。回顶新焦点都继续隐藏，composerTop=75px；取消隐藏后focalHidden=false，清理后标记/控制条/style均消失。
4. 同一个实验构建的13项自动测试覆盖photo子路由不再次抢滚动、初始hide=true使用composer锚点、再挂载重新标记、清理和不误藏composer。

**因此可以隐藏右侧焦点原帖，且所测视频样本中保留原生回复框、允许虚拟列表正常回收/重新挂载。** 不需要移动React节点，也不需要让右页原帖永远挂载。此结论仅限样本和注入路径，不能宣布所有媒体/分页通过。

`c1-public-replies-crop.png`只截取公开评论区域，排除账号导航和本人回复框；是右页隐藏后的局部展示，**不是双页/真实MV3截图**。

## 仍未证明

- 1280修复组base的y=10、composerTop=984，默认自动定位未在1秒采样点确认。10秒超时会提示用户手动滚动；不能把这一点改报PASS。
- 三个视口是单文档模拟视口，不是实际两窗口合计宽度；真正各半宽640/720等尚未验收。
- 两个可见原生页面初期可能各有播放器。CSS隐藏不保证无媒体资源开销，不能算单实例设计。
- article数增加仅表示新原生条目出现；没有验证每一条的真实回复祖先链或连续分页成功。
- C1未真实安装；chrome.tabs/windows、MV3消息/worker恢复尚只有mock。此前C研究只证明普通tabs之间生命周期隔离，未证明同时可见持续播放。
- T1/T2/T4/首次可播/资源成本未测，不通过性能Gate；M2-A +330.4ms异常仍未解释且维持NO-GO。
- Article、多图、GIF、投票、原生菜单/图片查看器/全屏完整专项未测；photo路由仅离线测试。
